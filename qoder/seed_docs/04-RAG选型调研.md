# RAG 方案选型调研（结论版）

## 背景
内部知识库问答需要同时支持关键词精确匹配与语义模糊查找，要求单库同时提供向量检索、全文检索和结构化过滤，并尽量减少组件数量。

## 候选对比
- 方案一：Elasticsearch + 独立向量插件。全文能力强，但向量部分需要额外维护，运维成本翻倍。
- 方案二：纯向量数据库 + 外接关键词模块。语义召回好，但关键词精确匹配（如单号、错误码）场景弱。
- 方案三：seekdb 一体化。同一实例内提供 VECTOR 向量列与 HNSW 索引、FULLTEXT 全文索引（IK 中文分词）、普通结构化列，MySQL 协议接入，一条 SQL 可以同时完成"全文过滤 + 向量排序"的混合检索。

## 结论
采用方案三。决定性因素：混合检索在一条 SQL 内完成，避免了多系统召回后的对齐与融合工程；且团队已有 MySQL 运维经验。核心语句形如：

```sql
SELECT id, content FROM chunks
WHERE MATCH(content) AGAINST('发票 报销')
ORDER BY l2_distance(embedding, '[...]') APPROXIMATE LIMIT 8;
```

## 遗留问题
中文长文档的分块策略对召回率影响明显，初步实验按标题分块、块长 400-600 字效果最好，后续需要用真实数据再校准。
